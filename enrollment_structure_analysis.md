Below is a structural analysis of the complete backend starter, based on your method map. I am not rewriting the project or suggesting UI changes.

Area / Method	Current Role in the File	Structural Issue	Why It Can Hurt Scalability or Maintainability	Layer-Design Problem
DB_PATH, SNAPSHOT_PATH	File-level configuration for database and JSON export paths	Global path constants are shared by every function	If the project grows, every database function is locked to one local database location. Testing also becomes harder because functions automatically use the same real file unless manually changed	Configuration is globally embedded instead of being passed into a database layer
CURRENT_STUDENT	Hardcoded sample student	Student identity is stored as global data	This is fine for practice, but in a real app the current student should come from a caller, not the backend file itself. Otherwise service logic becomes tied to one user	Application/demo state is mixed into backend logic
STATUS_ENROLLED, STATUS_UNENROLLED	Enrollment status constants	Status rules are global but not strongly controlled	The constants help avoid typos, but the database itself still accepts any text status unless protected elsewhere	Business rules exist outside the database schema and are loosely enforced
AVAILABLE_COURSE_KEYS	Seed data for courses	Static seed data lives in the same file as database and service behavior	This makes the file responsible for both application logic and sample data setup. As more courses or testing scenarios are added, the file becomes cluttered	Data seeding is mixed with backend behavior
SAMPLE_ENROLLMENTS	Seed data for enrollment records	Practice data is embedded directly in the backend file	The file becomes harder to read because it contains constants, database setup, service behavior, reporting, export logic, and demo flow	Seed/test data belongs closer to setup/demo responsibilities, not core service behavior
connect()	Opens SQLite connection	Database connection details are centralized, which is good, but still tied to global DB_PATH	This makes every database operation depend on one fixed database path. It also makes testing or switching databases harder later	Correctly database-layer, but depends on global configuration
create_tables()	Creates courses and enrollments tables	Schema creation is mixed into the same file as service functions	For a small assignment this is okay, but as the database grows, schema setup can become large and distract from business behavior	Database setup belongs to database layer, not service layer
seed_sample_data()	Inserts course and enrollment sample records	This function does database work and setup/demo work at the same time	It is not just “database behavior”; it is also deciding what initial practice data should exist. That can become messy if sample data changes often	Mixed same-layer/database setup plus demo-data responsibility
rows_to_dicts()	Converts SQLite rows to dictionaries	Helper function is tightly connected to SQLite result format	This is useful, but it exposes the fact that service functions are working directly with raw database rows	Boundary helper between database and service layers
get_available_course_keys()	Reads all course keys from database	You marked this as Service, but it mostly performs a database query	The function does not make much business decision beyond ordering. If many read methods stay at the service level, the service layer becomes full of SQL	Primarily database/repository behavior, not service behavior
get_course_by_key()	Looks up a course from an enrollment key	Database query also normalizes the key using strip().upper()	This is a good example of database code making a service-level decision. Input cleanup and key normalization are business/service concerns, while the query itself is database concern	Mixed: service validation/normalization + database query
get_student_enrollments()	Returns currently enrolled courses for a user	SQL directly applies the rule status = enrolled	The database query is not just fetching records; it is deciding what “current enrollment” means. If this rule changes, SQL must be updated inside the database access function	Database code is making a service-level filtering decision
get_student_enrollment_history()	Returns all enrollment records for a student	Mostly a read/query function, but still joined with course display data	This is useful, but it combines enrollment records with course details every time. That may become limiting if different callers need different shapes of data	Mostly database/repository behavior
get_student_course_record()	Returns one student-course enrollment record	Pure database lookup with basic input guarding	This is structurally cleaner than some other methods because it has one clear purpose. The only minor issue is that validation and querying are still in the same function	Mostly database/repository behavior with light service validation
enroll_with_key()	Enrolls or reactivates a student using a key	This is one of the most mixed methods in the file	It validates inputs, checks email format, finds a course, decides what to do when a prior record exists, performs an upsert, sets status to enrolled, updates timestamp, and returns a fresh record	Strong cross-layer mixing: validation + business rule + database write + database read
enroll_with_key()	Handles reactivation of unenrolled students	The “reactivate if previously unenrolled” rule is hidden inside SQL conflict behavior	This can be hard to maintain because a future reader must understand the SQL upsert to see the business rule	Service-level enrollment policy is buried in database code
enroll_with_key()	Uses get_course_by_key() and get_student_course_record()	One service action depends on other functions that also open database connections	This is fine in a small script, but with more complex transactions, multiple separate connections can become harder to manage	Transaction boundaries are not clearly controlled
soft_unenroll_student()	Changes status to unenrolled	This method is mixed, but less mixed than enroll_with_key()	It performs input validation, applies the business rule of soft unenrollment, writes to the database, and interprets rowcount as success/failure	Mixed: service-level decision + database update
soft_unenroll_student()	Updates any matching record regardless of current status	It does not check whether the student is currently enrolled before unenrolling	The function may report success even if the record was already unenrolled. That can make application behavior unclear later	Business rule is incomplete or implicit
get_student_summary()	Counts total, enrolled, and unenrolled records	Service-level aggregation depends on another service/database function	This is a service-style function because it computes meaning from records. However, it is tied to the exact shape returned by get_student_enrollment_history()	Service layer depends on database-returned dictionary structure
get_student_summary()	Loops through records in Python	Fine for small data, but less scalable for large enrollment histories	If many users or records exist, summary counts could be calculated more efficiently by the database. For learning, this is readable; for scale, it may become inefficient	Service computation may eventually need database aggregation
get_all_enrollment_records()	Returns every enrollment record for snapshot	You marked this as Service, but it is mostly a database read	It does not apply much business logic. It exists because the export function needs complete data	Mostly database/repository behavior
export_database_snapshot()	Builds and writes JSON snapshot	This is clearly cross-layer	It gathers current student data, available keys, all records, and writes a file. That combines application state, database reads, and file export responsibility	Mixed: service/data retrieval + file/export layer
export_database_snapshot()	Uses global CURRENT_STUDENT	Snapshot output is tied to one hardcoded student	If the project later supports multiple students, this function becomes misleading because the snapshot is not fully database-driven	Export logic reads global application/demo state
SQLite SELECT statements	Used throughout service-like methods	SQL is spread across many functions	This makes future database changes harder because many functions know the table structure directly	Database details leak across the whole backend file
SQLite INSERT / UPDATE statements	Used directly in behavior functions	Business actions are implemented directly as SQL	This is manageable now, but as rules grow, SQL and business decisions become tangled	Service and database layers are not separated
main()	Terminal demo runner	Demo flow is in the same file as backend behavior	The function initializes tables, seeds data, prints values, enrolls a student, summarizes, and exports. That is useful for practice but adds another responsibility to the file	Demo/application runner is mixed with backend logic
main()	Calls real database and export path	Running the file changes persistent local files	This can surprise students or testers because simply running the script mutates the database and writes a snapshot	Test/demo execution is not isolated from persistent storage
Overall file structure	One procedural backend file	Too many responsibilities live in one file	The file handles constants, seed data, database connection, schema creation, queries, enrollment behavior, summary reporting, JSON export, and demo running	Main structural problem: no clear separation between database, service, export, and runner responsibilities
Overall method map	Many functions are marked Service even though they contain SQL	Your map correctly notices several mixed methods, but some “Service” methods are actually database-heavy	This matters because a future EnrollmentManager could accidentally become a class full of SQL instead of a true service class	Service layer risks becoming a renamed database layer
Overall design	Procedural functions with repeated connect() usage	Each function manages its own database connection	This keeps functions simple, but transaction control becomes harder when one user action needs several database steps to succeed or fail together	Database lifecycle is scattered across functions
Overall design	Dictionaries are used everywhere	No clear data model boundary	Dictionaries are flexible, but they make the code dependent on exact string keys like "status", "course_id", and "email". Typos or shape changes can break other functions silently	Data shape is informal and shared across layers
Overall design	Enrollment rules are implicit	Important rules are not centralized	Rules like “valid email must contain @,” “blank key is invalid,” “unenroll means status change,” and “re-entering a key reactivates enrollment” are spread across functions	Business rules are scattered instead of grouped

Biggest structural issues to notice

Priority	Issue	Why It Matters
1	Database functions are also making service-level decisions	Several SQL-heavy methods decide what counts as active enrollment, how keys are normalized, how reactivation works, and whether an action succeeded
2	SQL is spread throughout the backend	If the schema changes, many functions may need edits
3	enroll_with_key() has too many responsibilities	It validates input, finds a course, applies business rules, writes to the database, and returns a result
4	Export logic is mixed with database and app/demo state	export_database_snapshot() pulls from multiple concerns and writes a file
5	The file combines backend logic, seed data, database setup, and demo runner	This is the core reason the design will become harder to maintain as the project grows

A simple way to understand the current design:

The file is not badly written for a starter assignment, but it is intentionally overloaded. The biggest learning point is that many functions look like service methods because their names describe student behavior, but inside they are doing direct database work. That is the main layer-design problem to recognize before refactoring.
